レプリケーション
（Replication）

データを複数の場所へ複製・同期する技術

レプリケーションとは？

レプリケーションとは、 データを別のサーバーや別の場所へ複製し、 同じ内容を同期する技術です。

主に、 データベース・クラウド・ストレージ・ Active Directory・分散システムなどで利用されます。

レプリケーションは、 「同じデータを複数の場所へ持たせる」 技術です。

まずはイメージで理解する

レプリケーションでは、 1台のサーバーのデータを、 他のサーバーにもコピーします。

Primary Server
↓ データ複製
Replica A
Replica B

「同じデータを複数台へ持たせて、 障害時でも継続利用できるようにする」 のがレプリケーションです。

レプリケーションは、 「サーバーが壊れても止まりにくくする」 ための重要技術です。

障害対策（冗長化）として利用される

1台だけで運用すると、 そのサーバーが故障した時に、 サービス全体が停止する可能性があります。

Primary 故障
↓
Replica が代わりに稼働

このように、 別サーバーへ切り替えることを 「フェイルオーバー」 と呼びます。

読み込み負荷を分散できる

大規模サービスでは、 読み込みアクセスが大量発生します。

そこで、 レプリカへ読み込み処理を分散し、 プライマリの負荷を軽減します。

User A → Replica A
User B → Replica B
User C → Replica C

書き込みはPrimary、 読み込みはReplicaへ分散する構成が 非常によく使われます。

災害・データセンター障害対策

レプリケーションは、 地震・停電・火災などの 地域障害対策でも重要です。

東京DC
⇅ レプリケーション
大阪DC

片方の地域が停止しても、 別地域でサービス継続できます。

同期レプリケーションとは？

同期レプリケーションでは、 Replica側への書き込み完了確認後に、 書き込み成功とみなします。

Primaryへ書き込み
↓
Replicaへ同期
↓
Commit成功

正常時は、 非常に高い整合性を維持できます。

ただし実際の分散システムでは、 ネットワーク分断や スプリットブレインなどにより、 完全な整合性維持が難しい場合もあります。

非同期レプリケーションとは？

非同期レプリケーションでは、 Primary側で先に書き込み完了を返し、 後からReplicaへ同期します。

Primary Commit
↓
Userへ成功返却
↓
後からReplica同期

非同期では、 「Replication Lag（同期遅延）」 が発生します。

Lag中にPrimaryが故障すると、 まだReplicaへ届いていない最新データが 消失する可能性があります。

Replication Lag（同期遅延）とは？

Replication Lagとは、 PrimaryとReplicaの間で発生する 同期の時間差です。

Primary : 最新状態
↓ 時間差
Replica : 少し古い状態

ネットワーク

通信遅延

高負荷

同期追いつかない

大量更新

転送量増加

遠距離DC

地理遅延

分散システムでは完全同期が難しい

分散システムでは、 複数サーバーがネットワーク越しに通信します。

そのため、 通信断や遅延が完全には避けられません。

CAP定理では、 「整合性・可用性・分断耐性」 を同時に完全実現できないとされています。

そのため実務では、 「絶対同期」 より、 「どこまで整合性を保証するか」 が重要になります。

バックアップの違い

レプリケーションとバックアップは、 似ていますが役割が異なります。

項目 レプリケーション バックアップ
目的 継続稼働 復元

世代管理 基本なし あり
誤削除耐性 弱い 強い

バックアップは「過去の状態」を
保存する

バックアップでは、 過去の特定時点の状態を保存できます。

今日の状態
↓
昨日の状態
↓
1週間前の状態

これを 「世代管理」 と呼びます。

ランサムウェアや誤削除対策では、 レプリケーションだけでなく、 世代管理付きバックアップが非常に重要です。

まとめ

レプリケーションとは、 データを別サーバーへ複製・同期し、 同じデータを複数箇所へ保持する技術です。

主に、 高可用性・負荷分散・災害対策・ 分散システム運用のために利用されます。

同期方式・非同期方式・ Replication Lag・CAP定理などを理解すると、 現代システム設計の考え方が非常に理解しやすくなります。

レプリケーションは、 「システムを止まりにくくする」 現代ITインフラの中核技術です。
